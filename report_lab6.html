2. Теоретические сведения

Нагрузочное тестирование (Load Testing) — вид тестирования программного обеспечения, предназначенный для оценки поведения, устойчивости и времени отклика системы при воздействии ожидаемой или пиковой нагрузки, формируемой множеством параллельных пользователей или процессов.

Locust — современный инструмент нагрузочного тестирования с открытым исходным кодом, в котором сценарии поведения пользователей описываются чистым кодом на языке Python. В отличие от классических инструментов на базе потоков ОС (таких как Apache JMeter), Locust использует легковесные микропотоки (корутины) библиотеки gevent. Это позволяет одному экземпляру Locust без существенных накладных расходов генерировать тысячи конкурентных HTTP-соединений с одного узла.

Ключевые концепции Locust:

  • HttpUser — базовый класс виртуального пользователя, предоставляющий клиента client (обёртка над requests.Session) для отправки HTTP-запросов и сбора телеметрии;
  • @task(weight) — декоратор, объявляющий метод сценарием взаимодействия. Параметр веса задаёт относительную частоту выбора задачи;
  • wait_time = between(min, max) — пауза между итерациями виртуального пользователя, имитирующая реальное поведение оператора (Think Time);
  • catch_response=True — механизм контекстного менеджера, позволяющий анализировать содержимое ответа (JSON-схему, статус-код) и явно фиксировать успех или сбой (response.success() / response.failure()).

Специфика тестируемых сервисов:

  • OpenBMC Redfish API: интерфейс управления сервером (драйвер bmcweb). Так как BMC функционирует на энергоэффективном процессоре архитектуры ARM с ограниченным объёмом оперативной памяти (256–512 МБ), частые запросы вызывают межпроцессные взаимодействия через системную шину systemd / D-Bus. Нагрузочное тестирование выявляет стабильность демонов телеметрии при непрерывном опросе.
  • JSONPlaceholder: публичный mock REST API, оптимизированный для тестирования клиентских библиотек. Имеет кэширование на уровне CDN и стабильное время ответа.
  • wttr.in: публичный консольный и веб-сервис погоды. Предоставляет сложные вычисления метеомоделей и накладывает строгие ограничения на частоту запросов (Rate Limiting), возвращая код 429 Too Many Requests при агрессивной нагрузке.

5. Реализация сценариев нагрузочного тестирования (locustfile.py)

5.1. Класс нагрузки OpenBMCUser

Класс моделирует обращение системных администраторов и агентов мониторинга к платформе OpenBMC. При старте виртуального пользователя в методе on_start отправляется POST-запрос авторизации для получения сессионного токена X-Auth-Token. Задачи распределены по весам: опрос информации о сервере (вес 3), проверка состояния питания (вес 2) и чтение термодатчиков (вес 1):

class OpenBMCUser(HttpUser):
    host = os.getenv("OPENBMC_HOST", "http://127.0.0.1:18443")
    wait_time = between(1.0, 2.5)
    weight = 3

    def on_start(self):
        """Аутентификация в OpenBMC Redfish API при запуске виртуального пользователя."""
        login_payload = {"UserName": "root", "Password": "0penBmc"}
        with self.client.post("/redfish/v1/SessionService/Sessions", json=login_payload,
                              name="[OpenBMC] POST /SessionService/Sessions (Auth)",
                              catch_response=True) as resp:
            if resp.status_code in (200, 201):
                token = resp.headers.get("X-Auth-Token") or resp.json().get("Token")
                if token:
                    self.client.headers["X-Auth-Token"] = token
                resp.success()
            else:
                resp.failure(f"Auth failed: {resp.status_code}")

    @task(3)
    def get_system_info(self):
        """Запрос паспорта системы (/redfish/v1/Systems/system)."""
        with self.client.get("/redfish/v1/Systems/system",
                             name="[OpenBMC] GET /Systems/system (System Info)",
                             catch_response=True) as resp:
            if resp.status_code == 200 and "PowerState" in resp.json():
                resp.success()
            else:
                resp.failure(f"Error {resp.status_code}")

    @task(2)
    def get_power_state(self):
        """Контроль состояния питания (PowerState)."""
        with self.client.get("/redfish/v1/Systems/system",
                             name="[OpenBMC] GET /Systems/system (PowerState)",
                             catch_response=True) as resp:
            if resp.status_code == 200 and resp.json().get("PowerState") in ("On", "Off"):
                resp.success()
            else:
                resp.failure("Invalid PowerState")

    @task(1)
    def get_thermal_telemetry(self):
        """Запрос температурных сенсоров (/redfish/v1/Chassis/chassis/Thermal)."""
        with self.client.get("/redfish/v1/Chassis/chassis/Thermal",
                             name="[OpenBMC] GET /Chassis/chassis/Thermal",
                             catch_response=True) as resp:
            resp.success() if resp.status_code == 200 else resp.failure("HTTP error")

5.2. Класс нагрузки PublicAPIUser

Класс выполняет нагрузку на внешние облачные REST-сервисы с верификацией целостности структуры возвращаемых JSON-документов:

class PublicAPIUser(HttpUser):
    host = "https://jsonplaceholder.typicode.com"
    wait_time = between(1.5, 3.0)
    weight = 2

    @task(3)
    def get_posts(self):
        """Запрос списка публикаций на JSONPlaceholder (/posts)."""
        with self.client.get("/posts", name="[Public] JSONPlaceholder GET /posts",
                             catch_response=True) as resp:
            if resp.status_code == 200 and isinstance(resp.json(), list):
                resp.success()
            else:
                resp.failure(f"Invalid response: {resp.status_code}")

    @task(1)
    def get_weather(self):
        """Запрос сводки погоды для Новосибирска на wttr.in."""
        weather_url = "https://wttr.in/Novosibirsk?format=j1"
        with self.client.get(weather_url, name="[Public] wttr.in GET Novosibirsk Weather",
                             catch_response=True, timeout=10.0) as resp:
            if resp.status_code == 200 and "current_condition" in resp.json():
                resp.success()
            elif resp.status_code == 429:
                resp.failure("Rate limited (429)")
            else:
                resp.failure(f"HTTP {resp.status_code}")

7.3. Оценка максимальной нагрузки и анализ точек отказа

1. Характер задержек и производительность:

  • OpenBMC Redfish API: показал наивысшую стабильность и наименьшие задержки (в среднем 16 мс, 95-й перцентиль 18 мс). Малое время отклика обусловлено отсутствием внешней глобальной сети и эффективной архитектурой локального диспетчера запросов.
  • JSONPlaceholder: показал среднее время отклика 253 мс (с пиками до 380 мс). Задержка формируется RTT сетевого маршрута до зарубежного облачного провайдера и обработкой полезной нагрузки объёмом ~27 КБ на запрос.
  • wttr.in: показал наибольшую задержку (в среднем 500 мс, 95% перцентиль 810 мс), что связано с динамической генерацией подробного метеорологического прогноза объёмом ~40 КБ и работой бэкенда геопозиционирования.

2. Возможные точки отказа (Bottlenecks):

  • На стороне OpenBMC: аппаратные ресурсы управляющего микроконтроллера BMC жёстко лимитированы. При возрастании нагрузки свыше 50–100 одновременных пользователей или превышении частоты 50 RPS узким местом станет межпроцессная синхронизация bmcweb с шиной D-Bus (служба xyz.openbmc_project.State.Host), что приведёт к росту очереди задач, исчерпанию пула дескрипторов сокетов и деградации производительности. Дополнительной точкой отказа является ограничение таблицы активных сессий в SessionService.
  • На стороне внешних сервисов: публичные API защищены алгоритмами ограничения частоты запросов (Rate Limiting / Token Bucket). При превышении допустимого порога обращений (более 2–3 запросов/сек с одного IP на wttr.in) сервер начнёт возвращать ошибку 429 Too Many Requests либо принудительно обрывать TCP-соединение.
